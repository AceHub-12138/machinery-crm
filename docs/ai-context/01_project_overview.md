# 02｜CRM / ERP 项目总纲：DachuanPro

## 一、项目定位

DachuanPro 是大川机床内部使用的 CRM/ERP 平台，起点是客户管理系统，后续扩展为覆盖销售、合同、回款、发货、物料、库存、BOM、采购、生产和成本的内部业务系统。

系统不是对外销售软件，主要服务公司内部 4-6 人及后续扩展人员。

## 四、CRM 已有核心模块

### 1. 客户管理

- 新老客户资料集中管理。
- 客户按区域、业务线、销售权限隔离。
- 客户可以绑定多个产品兴趣标签。
- 客户详情页关联报价、合同、回款、跟进、发货等信息。
- 支持客户筛选、修改、删除或软删除相关流程。

### 2. 产品管理

- 建立产品库。
- 产品可关联出厂价格、选配项、图片/资料。
- 报价时可带出产品出厂价作为参考。
- 报价记录应保存出厂价快照，避免后续产品价格变化影响历史报价。

### 3. 报价管理

- 客户可新增报价。
- 报价与产品价格联动。
- 支持从报价一键转合同。
- 历史报价需要保留快照，不能因产品库变化而变形。

### 4. 合同管理

- 合同字段包括：签订日期、合同编号、销售对接人员、客户名称、设备名称、设备型号、设备金额、合同附件、备注等。
- 合同支持已成交、已做合同未打款等分类。
- 合同可关联多个产品/设备明细，历史上确认多品子表 `contract_items` 是主设计。
- 合同删除应走超级管理员审批或软删除，不应直接硬删。
- 已发货、已完成、已归档合同应锁定，修改需要审批。

### 5. 回款管理

- 支持部分回款金额。
- 支持回款日期。
- 新合同金额低于当前已收款金额时，不能自动覆盖。
- 回款修改应有日志或审批，避免财务数据被随意改动。

### 6. 发货/地图

- 工作台曾集成高德地图，后因成本和限制切换到天地图。
- 发货路径图目标是科技感、航线/路径视觉。
- 地图 Key 应放在服务端 `.env`，前端不应直接泄露敏感 Key。
- 天地图 Leaflet 资源曾本地化/代理化处理。

### 7. 权限系统

系统已从简单区域权限逐步升级为二维权限：

- 业务线：国内销售 / 外贸
- 区域：省 / 市 / 片区
- `viewScope`：TERRITORY / ALL
- 角色：SUPER_ADMIN、SALES、FOREIGN_TRADE，ERP 后增加 WAREHOUSE
- 权限原则：默认拒绝，按角色、业务线、区域显式授权。
- 权限必须每次请求从数据库读取最新状态，避免旧 session 缓存导致权限失效。

### 8. 日志与审批

- 系统已有审批、日志、锁定相关机制。
- 后续所有高风险操作，如合同删除、合同解锁、回款修改，应走审批和日志。

## 五、ERP 阶段定位

ERP 优先于 MES。原因：

- 大川机床属于低批量、高复杂度的机床制造。
- 当前最急需的是物料、BOM、库存、采购、订单进度、成本核算。
- MES 更适合高频重复制造，后续可做轻量生产进度，不宜一开始重做 MES。
- ERP 的物料/BOM/库存是后期 MES 和 IoT 的基础。

## 六、ERP Phase 1 已知内容

ERP 第一期已部署/设计过以下基础：

- 13 张 `erp_` 开头的表。
- 物料管理。
- 物料分类。
- BOM 表头和 BOM 明细。
- 入库。
- 出库。
- 盘点。
- 库存流水台账 StockMovement。
- 仓管角色 WAREHOUSE。
- ERP 访问权限限制。
- BK5030 物料数据，历史记录中提到约 114 个物料、7 个分类。
- 出入库使用事务。
- 出库前检查库存是否足够，避免扣成负数。
- 明细使用子表，而不是 JSON 大字段。

## 七、ERP 已发现并需要持续关注的问题

1. 出入库并发竞态：不能长期使用“先读库存→计算→写回”的方式，后续应改为原子更新或加锁。
2. 同一单据重复物料：如果一张出库单里同一物料出现多行，库存检查可能漏算，需要合并校验。
3. `db:reset` 脚本仍然危险，生产环境绝对不能执行。
4. ERP 分支曾出现 orphan branch / 无共同祖先风险，不能直接部署旧分支覆盖 main。
5. 合并 ERP 时必须保留线上 main 的登录页、权限系统、PWA、天地图、安全加固等新功能。
6. ERP 不能照搬旧版 sidebar、permissions、schema，必须嫁接到现有 main。
7. 新增 WAREHOUSE 角色时不能破坏原 SALES / FOREIGN_TRADE / SUPER_ADMIN 权限。

## 八、开发方法

正确方式：

1. 以线上 main 为唯一基准。
2. 从 ERP 分支中提取有效模块。
3. 手工嫁接到 main。
4. 所有数据库变更必须是纯新增或安全 ALTER。
5. Codex 生成代码后，AI 必须复核。
6. GitHub Actions 构建部署包。
7. 用户再按部署脚本执行。
8. 出问题必须有回滚包。

错误方式：

- 直接把 erp-phase1 分支部署到服务器。
- 用旧分支覆盖 main。
- 在生产执行 `db:reset`。
- 让服务器直接跑耗内存的完整构建。
- 没有备份就导入 SQL。
- 跳过 AI 审查直接上线 Codex 产物。
